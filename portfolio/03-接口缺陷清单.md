## 二、缺陷清单（按严重程度排序）

### BUG-01【高】未发货订单可以直接确认收货

- **关联用例**：FORDER-005、E2E-019
- **前置条件**：订单已付款、已确认，`shipping_status=0`（未发货）
- **复现步骤**：`POST /index.php?m=Home&c=Order&a=order_confirm`，body `order_id=2257`
- **实际结果**：返回 `{"status":1,"msg":"操作成功"}`；订单 `order_status=2`（已收货）、`shipping_status=0`
- **预期结果**：拒绝并提示"订单未发货，不能确认收货"
- **影响**：可绕过发货环节直接把订单推进到待评价，订单状态与实物不一致，接入售后/结算后存在资损风险
- **根因**：`confirm_order()` 只校验 `order_status==1` 与付款状态，未校验 `shipping_status`
- **修复建议**：`confirm_order()` 增加 `shipping_status == 1` 校验
- **证据**：`tp_order` order_id=2257

### BUG-02【高】未支付 / 未确认的订单可以直接发货

- **关联用例**：E2E-016、E2E-017
- **前置条件**：订单未支付（2258）或已付款但未确认（2259）
- **复现步骤**：
  1. `GET /index.php/admin/Order/delivery_info/order_id/{订单ID}` 取 rec_id
  2. `POST /index.php/Admin/order/deliveryHandle`，body 含 `goods[]=rec_id&order_id={订单ID}`
- **实际结果**：返回"操作成功"；`order_goods.is_send=1`，订单 `shipping_status=1`
  - 2258：`pay_status=0`；2259：`order_status=0`
- **预期结果**：未支付/未确认订单不允许发货
- **影响**：可跳过付款与确认环节直接发货，形成"未付款已发货"的资损风险
- **根因**：`deliveryHandle()` 未校验订单支付状态与确认状态
- **修复建议**：发货前校验 `pay_status==1 && order_status==1`
- **证据**：order_id 2258、2259

### BUG-03【高】已取消订单可以再次确认付款并"复活"

- **关联用例**：ADMORDER-009
- **前置条件**：订单已取消（`order_status=3`）
- **复现步骤**：
  1. 前台下单后调用 `POST /index.php?m=Home&c=Order&a=cancel_order`，body `id=2260`
  2. 后台调用 `POST /index.php/Admin/order/order_action/type/pay?order_id=2260`
- **实际结果**：取消后 `order_status=3`；付款后 `order_status=0`、`pay_status=1`
- **预期结果**：已取消订单不允许付款，状态保持已取消
- **影响**：取消订单可被重新激活，影响库存、财务与售后数据一致性
- **根因**：`update_pay_status()` 只校验 `pay_status`，未校验 `order_status`
- **修复建议**：付款前校验订单状态（已取消/已完成不可付款）
- **证据**：order_id 2260

### BUG-04【高】水平越权：可以使用他人的收货地址下单

- **关联用例**：CART-017b
- **前置条件**：用户 A（4578）有地址 `address_id=135`；用户 B（4624）无地址
- **复现步骤**：B 登录后加购，提交订单时传 `address_id=135`（A 的地址）
- **实际结果**：返回"提交订单成功"；订单 2275 归属 B（user_id=4624），但收货人/手机/地址为 A 的 `测试收货人 / 177****5092 / 省份1 城市2 区3 地址11`
- **预期结果**：拒绝使用他人地址，提示地址无效
- **影响**：泄露他人姓名、手机号、详细地址，并可把商品寄往他人地址
- **根因**：`cart3()` 只按 `address_id` 查询地址（`Cart.php:330`），未校验 `user_address.user_id`
- **修复建议**：查询地址时增加 `user_id = 当前登录用户` 条件
- **证据**：order_id 2275；`tp_user_address.address_id=135`

### BUG-05【高】水平越权：可以为他人订单发起支付

- **关联用例**：PAY-006
- **前置条件**：用户 A 有未支付订单 2266；用户 B 已登录
- **复现步骤**：B 向 `POST /index.php/Home/Payment/getCode.html` 传 `order_id=2266`（A 的订单）
- **实际结果**：返回 200 支付页；A 的订单被写入 `pay_code=cod`
- **预期结果**：拒绝操作，不修改他人订单
- **影响**：可篡改他人订单支付方式，配合回调可把他人订单置为已支付，资金与订单归属风险
- **根因**：`Payment::getCode()` 只校验登录态，未校验 `order.user_id`
- **修复建议**：查询订单时增加 `user_id = session('user').user_id`
- **证据**：order_id 2266（user_id=4578，pay_code=cod，pay_status=0）

### BUG-06【中】发货失败不是原子操作，失败后残留发货单

- **关联用例**：ADMORDER-016、ADMORDER-016b、ADMORDER-016c
- **前置条件**：后台已登录；订单已付款待发货
- **复现步骤**：
  1. 发货时不传 `goods[]`（或传 `goods=2559` 字符串）
  2. 查询 `tp_delivery_doc`、`tp_order_goods`、`tp_order_action`
- **实际结果**：接口 500（`in_array() expects parameter 2 to be array, null given / string given`）；`tp_delivery_doc` 新增一条；`order_goods.is_send=0`；无"确认发货"操作日志
- **预期结果**：参数非法返回 400/业务错误，且不产生任何数据变更
- **影响**：每次失败都会累积无效发货单，发货记录与面单被污染
- **根因**：`deliveryHandle()` 先写 `delivery_doc`（`OrderLogic.php:779`），再在循环里执行 `in_array`（第 794 行），异常后无事务回滚
- **修复建议**：参数校验前置；发货单与商品状态更新放入同一事务
- **证据**：order_id 2256（发货单 2 条、is_send=0）；order_id 2243 同样 2 条

### BUG-07【中】并发发货会产生重复发货单

- **关联用例**：E2E-027b
- **前置条件**：订单已付款并确认待发货
- **复现步骤**：同一时刻并发提交两次 `deliveryHandle`（相同 `goods[]`、`order_id`）
- **实际结果**：一次返回"操作成功"，但 `tp_delivery_doc` 生成 2 条记录（order 2270）
- **预期结果**：只生成 1 张发货单，重复请求应幂等拦截
- **影响**：重复发货单、重复面单、物流信息重复
- **修复建议**：发货前校验 `shipping_status`，或对 `order_id+rec_id` 加唯一约束/分布式锁
- **证据**：order_id 2270，`tp_delivery_doc` 计数=2

### BUG-08【中】不存在的收货地址仍能生成订单

- **关联用例**：CART-017
- **前置条件**：前台已登录
- **复现步骤**：提交订单传 `address_id=999999`（不存在）
- **实际结果**：返回"提交订单成功"；订单 2253 的 `province/city/district=0`、`address=""`
- **预期结果**：提示收货地址无效，不生成订单
- **影响**：可生成无收货地址订单；实测订单 2252 在空地址下仍完成付款、发货、收货、评价全流程
- **根因**：`cart3()` 只做 `address_id require` 校验，未校验地址是否存在及归属
- **修复建议**：地址不存在或不属于当前用户时拒绝下单
- **证据**：order_id 2253（空地址）；order_id 2252（空地址但已完成，状态 4/1/1）

### BUG-09【中】参数异常时多处返回 500 而不是业务错误

- **关联用例**：ADMORDER-003、ADMORDER-011、ADMORDER-016
- **复现与结果**：
  | 请求 | 实际 |
  |---|---|
  | `POST /index.php/Admin/order/order_action/type/confirm?order_id=999999` | 500 `SQLSTATE[23000]: Column 'order_id' cannot be null` |
  | `GET /index.php/admin/Order/delivery_info/order_id/999999` | 500 `Call to a member function append() on null` |
  | `POST /index.php/Admin/order/deliveryHandle`（缺 `goods[]`） | 500 `in_array() expects parameter 2 to be array, null given` |
- **预期结果**：返回 400 或明确业务提示，不暴露代码/堆栈信息
- **影响**：接口健壮性差；错误信息暴露文件路径与代码结构，存在安全风险
- **修复建议**：统一参数校验与异常处理，生产环境关闭 `app_debug`

### BUG-10【中】登录响应返回密码与支付密码哈希

- **关联用例**：AUTH-030x
- **复现步骤**：`POST /index.php?m=Home&c=User&a=do_login`，查看响应体
- **实际结果**：响应 `result` 中包含 `"password":"519475228fe35ad067744465c42a19b2"`、`"paypwd":"519475..."`（均为 md5 哈希）
- **预期结果**：登录响应只返回必要用户信息，不返回密码/支付密码字段
- **影响**：哈希可被离线爆破（`md5(TPSHOP+明文)`），支付密码哈希泄露影响资金安全
- **修复建议**：响应字段白名单，剔除 `password`、`paypwd` 等敏感字段

### BUG-11【中】未登录可以加入购物车，并写入共享的 user_id=0 购物车

- **关联用例**：CART-011
- **复现步骤**：不携带登录态调用 `POST /index.php?m=Home&c=Cart&a=add`（goods_id=1，goods_num=1）
- **实际结果**：返回 `{"status":1,"msg":"加入购物车成功"}`；`tp_cart` 新增 `id=30, user_id=0, goods_id=1, goods_num=1`
- **预期结果**：拒绝加购或跳转登录；即使允许游客购物车，也应与会话绑定
- **影响**：所有未登录用户共用 `user_id=0` 的购物车，存在数据串号与隐私问题
- **修复建议**：加购要求登录；如支持游客，使用 session/guest_id 作为购物车归属
- **证据**：`tp_cart` id=30

### BUG-12【中】评价评分没有上限校验

- **关联用例**：FORDER-009b
- **复现步骤**：`POST /index.php/Home/Order/add_comment.html`，`goods_rank=6`，其余正常
- **实际结果**：返回"评论成功"，`tp_comment.goods_rank=6` 落库
- **预期结果**：评分范围 1~5，6 应拒绝
- **影响**：评分统计异常，前端展示可能出错
- **根因**：`UsersLogic::add_comment()` 只校验 `<1`，未校验 `>5`
- **证据**：order_id 2262，comment.goods_rank=6

### BUG-13【低】评价内容为空仍然评论成功

- **关联用例**：FORDER-010a
- **复现步骤**：`add_comment.html` 传 `content=`（空）
- **实际结果**：返回"评论成功"；`tp_comment.content` 长度 0
- **预期结果**：拒绝空内容
- **影响**：产生无内容评价，污染商品评价数据
- **证据**：order_id 2263，`CHAR_LENGTH(content)=0`

### BUG-14【低】负数购买数量加购成功并落库为 0

- **关联用例**：CART-006a
- **复现步骤**：`POST /index.php?m=Home&c=Cart&a=add`，`goods_num=-1`
- **实际结果**：返回"加入购物车成功"；`tp_cart.goods_num=0`
- **预期结果**：拒绝负数量与 0 数量，提示参数错误
- **影响**：购物车出现 0 数量商品，结算时可能产生 0 元订单或异常
- **证据**：加购后 `tp_cart` 最新行 `goods_num=0`

### BUG-15【低】提交订单的 auth_code 未被校验

- **关联用例**：CART-018
- **复现步骤**：提交订单时 `auth_code=TEST`（文档要求 TPSHOP）
- **实际结果**：仍返回"提交订单成功"，生成订单 2254
- **预期结果**：auth_code 错误应拒绝提交
- **影响**：文档声明的认证标记形同虚设，降低接口防护能力
- **证据**：order_id 2254

### BUG-16【低】重复后台付款返回"操作成功"但未产生任何变更

- **关联用例**：ADMORDER-008
- **复现步骤**：对已完成订单 2252 再次调用后台付款
- **实际结果**：返回 `{"status":1,"msg":"操作成功"}`；订单状态仍为 4、无 new 变更
- **预期结果**：提示"订单已付款"或"状态不允许"
- **影响**：误导操作人员，无法判断是否重复记账
- **建议**：返回明确的业务提示

### BUG-17【低】支付状态页跨用户回显订单号

- **关联用例**：PAY-012
- **复现步骤**：用户 B 访问 `/index.php/home/Payment/returnUrl/pay_code/cod/order_sn/{A的订单号}.html`
- **实际结果**：页面正常返回并回显 A 的订单号
- **预期结果**：校验订单归属，不向其他用户展示订单信息
- **影响**：订单号信息泄露（低危）；同时该页面是静态回显，不能作为支付成功判据
- **建议**：校验登录用户与订单归属；支付状态页从订单真实状态渲染

## 四、复测通过项（摘要）

- 全链路主流程：登录 → 加购 → 下单 → 获取订单 ID → 货到付款 → 后台付款 → 确认订单 → 发货 → 确认收货 → 评价，订单 2252 最终 `order_status=4 / pay_status=1 / shipping_status=1 / is_send=1 / is_comment=1`。
- 有效地址 135 下单：订单 2274 收货信息正确（测试收货人 / 177****5092 / 省1 市2 区3 / 11）。
- 登录 SQL 注入失败（参数化查询生效）。
- 评价 XSS 被转义：落库 `&lt;script&gt;alert(1)&lt;/script&gt;`，详情页未执行（order 2264）。
- 未登录调用支付/确认收货/评价/后台接口均被拒绝。
- 跨用户 `cart4` 查订单、跨用户确认收货被拒绝（订单归属校验生效）。
- 并发提交订单仅生成 1 单；并发评价仅 1 条；并发确认收货 1 次成功；并发付款仅 1 条"付款成功"日志。
- 库存扣减时点符合 `reduce=2`：下单不扣（610→610），付款扣 1（610→609，order 2276）。
- 取消未支付订单后库存回补（order 2273，库存 610）。
